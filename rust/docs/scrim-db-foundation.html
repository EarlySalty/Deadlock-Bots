Scrim-DB-Foundation 2026072408..2416

Versionierter technischer Foundation-Vertrag für die Datenbank-Migrationen 2026072408 bis 2026072416. Die Dokumentation fasst die Schema-, Runtime-, Queue-, Result-, Steam-V1- und Privacy-Verträge zusammen.

Scope und Nicht-Scope

Die Foundation ist eine additive Datenbankbasis für Scrim-Runtime-Steuerung, idempotente Workflows, Result-Auswahl, Steam-V1-Persistenz und Privacy-Klassifikation. Die bestehenden Writer werden dadurch nicht ersetzt.

Der aktuelle Runtime-Seed bleibt legacy mit operational_writer = 'dl-bots'. Die Migrationen legen Umschalt- und Audit-Verträge an, schalten aber keinen Turniere-Writer produktiv und aktivieren keinen Steam-V1-Consumer.

Die Identity-Cutover der bestehenden Scrim-Tabellen ist ausdrücklich nicht enthalten. Die Tests sichern ab, dass scrim.participants.id, scrim.teams.id, scrim.matches.id, scrim.match_request_batches.id und scrim.match_requests.id keine Identity-Defaults erhalten.

Runtime-Control, CAS, Historie und Audit

Runtime-Modell

scrim.runtime_control_history ist die einzige persistente Runtime-State-Quelle. scrim.runtime_control ist eine nicht aktualisierbare View auf die neueste Historienzeile je control_key.

  • control_key ist immer scrim_runtime.
  • mode ist genau legacy, draining oder turniere.
  • operational_writer ist genau dl-bots oder turniere.
  • Erlaubte Kombinationen: legacy/dl-bots, draining/turniere, turniere/turniere.
  • Erlaubte Übergänge: legacy -> draining, draining -> legacy, draining -> turniere, turniere -> draining.
  • Epochs sind fortlaufend. Seed ist epoch = 0, mode = legacy, operational_writer = dl-bots.

Updates, Deletes und Truncates auf der Historie werden mit SQLSTATE 55000 verhindert. Inserts werden per Advisory-Transaction-Lock (724060001, 724060002) serialisiert.

Queues, Idempotenz und terminale Regeln

Die Queue-Tabellen sind Journale. Identitätsfelder sind nach Insert unveränderlich, außer explizit erlaubte Privacy-Redactions. Deletes und Truncates sind blockiert. Payload- und Fehler-Hashes sind immer 32 Byte. Technische Textfelder sind entweder bounded Machine-Codes oder Domain-Refs im Schema namespace:wert; nackte User-IDs und Display-Namen werden dort per Constraint abgewiesen.

Gemeinsame Idempotenzregeln

  • Dieselbe Generation eines Idempotenzschlüssels ist dauerhaft eindeutig, auch nach terminalem Abschluss.
  • Nach terminalem Abschluss darf eine höhere Generation angelegt werden, solange keine andere aktive Generation existiert.
  • Identity-Felder wie Scope, Key, Generation, Payload-Hash und Payload können nicht nachträglich umgeschrieben werden.
  • Terminale Zustände sind final. Reopen-Versuche werfen 55000.
  • last_error_code ist nur err_[a-z0-9_]{2,64}; roher Fehlertext oder User-ID-ähnliche Fehlerwerte werden nicht gespeichert.

Result-Selection-Vertrag

Erweiterung von scrim.match_result_refs

Die Migration erweitert die bestehende Tabelle additiv um:

  • external_result_ref TEXT
  • validation_status TEXT NOT NULL DEFAULT 'unvalidated'
  • clarification_state TEXT NOT NULL DEFAULT 'none'
  • clarification_payload JSONB NOT NULL DEFAULT '{}'
  • is_selected BOOLEAN NOT NULL DEFAULT false
  • selected_at TIMESTAMPTZ
  • selected_by_user_id TEXT
  • selection_reason TEXT als Machine-Code
  • voided_at TIMESTAMPTZ
  • void_reason TEXT als Machine-Code
  • superseded_by_ref_id BIGINT

validation_status ist genau unvalidated, valid, ambiguous, rejected, void oder superseded. clarification_state ist genau none, needed, requested, resolved oder cancelled.

Reason-Felder sind keine Freitexte. match_result_refs.selection_reason, match_result_refs.void_reason und match_result_selections.selection_reason muessen bounded Machine-Codes im Format ^[a-z][a-z0-9_]{2,63}$ sein. Menschliche Details, Namen oder freie Begruendungen gehoeren in Clarification-Payloads.

match_id verweist per ON DELETE RESTRICT auf scrim.matches(id). superseded_by_ref_id verweist per ON DELETE RESTRICT auf scrim.match_result_refs(id), darf nicht auf sich selbst zeigen, wird per Trigger auf denselben Match beschränkt und darf keine direkten oder indirekten Supersession-Zyklen bilden. Lock-Reihenfolge fuer Graph-Mutationen: zuerst transaction advisory lock im festen Namespace 2026072411 mit match_id, danach Ziel-Ref-Lookup und rekursive Zykluspruefung.

Canonical Selection
Objekt Kontrakt

Actor-Felder: selected_by_user_id, selected_by_display_name. selection_reason ist ein nicht-personaler Machine-Code. Genau eine aktuelle Auswahl je Match wird gehalten. Auswahlbedingung Ein Result-Ref darf nur canonical ausgewählt werden, wenn es zum Match gehört, validation_status = 'valid', fetch_status = 'fetched', steam_match_id IS NOT NULL, winner_team_id IS NOT NULL, voided_at IS NULL und superseded_by_ref_id IS NULL gilt.
Invalidierungsblockade Ist ein Ref in scrim.match_result_selections ausgewählt, blockiert ein Trigger spätere Änderungen, die es nicht mehr fetched, valid, unvoided, current oder winner-vollständig machen würden. Eine Reselection muss einen anderen Ref setzen, Actor und Grund neu angeben und ein neueres selected_at nutzen. Der neue Ref wird beim Schreiben gesperrt, damit parallele Invalidierung erst nach Commit erneut gegen die aktuelle Auswahl geprüft wird.

Ergebnis-Spalten: match_id, result_ref_id, steam_match_id, winner_team_id, result_json, source, selected_at, selected_by_user_id. source ist result_ref, wenn ein gültiger selected Ref existiert, sonst NULL.

Legacy-Flag ist nicht canonical. Das alte is_selected an scrim.match_result_refs reicht nicht für scrim.selected_match_results. Canonical ist ausschließlich ein Eintrag in scrim.match_result_selections. Die nicht notwendige Live-Indexierung auf match_result_refs wird in dieser Foundation bewusst zurückgestellt.

Backfill

Vor dem Backfill prüft 2026072413, ob ein Legacy-steam_match_id aus scrim.matches bereits als Result-Ref eines anderen Matches existiert. Bei Konflikt bricht die Migration mit 23505 ab.

Backfill-fähig sind Matches mit steam_match_id, winner_team_id, result_json und Status finished oder completed beziehungsweise lobby_state = 'finished'. Bestehende passende Result-Refs werden vervollständigt, fehlende passende Refs werden als valid und fetched angelegt. Die canonical Auswahl wird deterministisch nach fetched_at, updated_at, entered_at, steam_match_id und id absteigend bestimmt, je Match aber nur wenn noch keine Auswahl existiert. Der Migration-Actor nutzt eine synthetische numerische ID, damit Audit-Pseudonyme nie aus Freitext-User-Refs entstehen.

Clarifications

scrim.match_result_clarifications speichert Klärungen mit clarification_kind missing_result, ambiguous_winner, conflicting_ref oder manual_review. status ist open, requested, resolved oder cancelled. resolved_at ist nur bei resolved oder cancelled gesetzt.

Privacy, DSAR und Erasure

SQL-Erasure-Gate

Die SQL-Funktionen aus 2026072409 erlauben Privacy-Redaction nur in einer gesetzten Privacy-Transaktion:

  • scrim.privacy_erasure_user_id muss eine numerische User-ID enthalten.
  • core.user_privacy muss für diese User-ID opted_out = true und deleted_at IS NOT NULL enthalten.
  • scrim.privacy_erasure_target_ref ist entweder dieselbe Discord-ID, eine über core.steam_links verbundene steam_id/steam_id64 oder eine daraus sicher abgeleitete Steam-Account-ID.
  • Ohne exakten Target-Bezug bleibt Redaction verboten und die Append-only-Guards werfen 55000.

scrim.jsonb_contains_user_ref findet Target-Refs rekursiv in JSON-Objektkeys, Arrays, Strings und Zahlen. scrim.jsonb_redact_user_ref entfernt Objektkeys, die exakt dem Target entsprechen, und ersetzt passende String- oder Zahlenwerte durch "redacted".

Der bestehende Pfad löscht die core.steam_links-Zeilen des Users.
Legacy-Fehlertext scrim.match_result_refs.last_error, scrim.match_requests.override_reason und scrim.match_requests.status_message_last_error bleiben aus Kompatibilitätsgründen Text. DSAR exportiert sie nur als Hash oder Redaction; Erasure ersetzt exakte Discord-, Steam64- und Account-ID-Targets durch redacted, ohne die Writer-Schnittstellen zu ändern. Teiltreffer wie 4242 oder user42 werden nicht angefasst.

DSAR-Export

Der Privacy-Vertrag erweitert den DSAR-Export um Foundation-Tabellen. Exportierte JSON-Zeilen werden subjektbezogen projiziert: Ziel-Refs bleiben sichtbar, fremde User-/Steam-Refs, fremde Display-Namen und fremde Payload-Anteile werden redigiert oder als md5-Digest ausgegeben. Der generische JSON-DSAR exportiert nie ganze Tabellenzeilen, sondern nur stabile Row-ID plus genau die angefragte JSON-Spalte; benachbarte Freitexte, manuelle Review-Payloads, Message-ID-Maps oder Lobby-Secrets bleiben dadurch unsichtbar. Result-Payloads aus Legacy-Matches und Result-Refs laufen durch denselben Projektor: Ziel-Spielerdaten bleiben sichtbar, fremde Player-Objekte, fremde Account-IDs und fremde Namen nicht. Lobby-Code-Korrekturen, Replacement- und Clarification-Payloads bleiben in der automatischen JSON-Erasure, nutzen im DSAR aber explizit HashOnly: pro betroffener JSON-Spalte wird nur id plus Payload-Digest ausgegeben, nie Rohdaten, Lobby-Codes, Notizen oder Projektionen. Die Actor-Exports behalten ihre fachlichen Hash-Nachweise. Selection-Historie wird über das Actor-Pseudonym exportiert; Ref-Wechsel bleiben über old_result_ref_id und new_result_ref_id sichtbar, während Snapshot-JSON nur als Hash erscheint. Dadurch bleiben Nachweiszeilen sichtbar, ohne fremde personenbezogene Inhalte offenzulegen.

Für Actor-getriebene Tabellen werden fachliche Inhalte wie Announcement-Text, freie Gründe, Lobby-Codes, Join-/Party-Secrets oder fremde JSON-Kontexte nicht ungeprüft offengelegt, sondern ausgelassen, redigiert oder gehasht. scrim.matches und scrim.match_requests haben explizite sichere Actor-Projektionen: Actor-, Domain-, Status- und Zeit-Metadaten bleiben sichtbar, Result-/Correction-/Slot-Payloads, Message-ID-Maps, Override-Gründe und Fehlertexte nur als Hash oder Redaction. AI- und Steam-V1-Exports folgen derselben kind-aware Logik wie die Erasure.

Privacy-Feldregister

core.privacy_field_registry ist Primärschlüssel (schema_name, table_name, column_name). Die erlaubten Kategorien sind exakt:

  • data_category: user_id, display_name, json_payload, free_text, domain_id, machine_code, content_hash, pseudonym
  • retention_action: retain_operational, retain_audit, expire_with_domain, manual_review
  • erasure_action: redact_on_user_delete, delete_row_on_user_delete, retain_hash_only, retain_non_personal, manual_review

Das Register klassifiziert Foundation-Felder per owner_service und reason. Tests prüfen, dass Registry-Zeilen nicht auf fehlende Spalten zeigen, direkte IDs/Pseudonyme nicht als manual_review versteckt sind und Audit-JSON mit manual_review einen Grund zur Raw-Actor-Trennung oder typed-column-Separation dokumentiert. machine_code- und domain_id-Labels brauchen zusätzlich echte CHECK- oder FK-Struktur; ein Registry-Claim allein reicht nicht.

Rollout, Preflight, Verifikation und Rollback

Betriebshaltung der Foundation
Phase Faktischer Stand
Additiver Rollout Neue Tabellen, Views, Funktionen, Trigger, Constraints und Registry-Zeilen werden additiv angelegt. Bestehende Writer bleiben auf Legacy-Pfaden. scrim.match_result_refs wird erweitert, aber nicht durch neue nichtkonkurrente Live-Indizes belastet. Die dynamischen SQL-Helper scrim.ensure_check_constraint und scrim.validate_constraints sind nur migrationsintern und werden am Ende von 2026072416 wieder entfernt.
Preflight Vor dem Backfill bricht 2026072413 ab, wenn ein Legacy-steam_match_id bereits einem Result-Ref eines anderen Matches zugeordnet ist. lock_timeout = 2s verhindert langes Warten auf blockierte DDL. Neue technische CHECKs werden in den jeweiligen Migrationen validiert; 2026072414 validiert zusätzlich Result-Ref-, Selection- und Clarification-Constraints und bricht ab, wenn eine erwartete Constraint unvalidiert bleibt.
Verifikation Die Foundation-Tests scrim_db_foundation.rs prüfen Tabellen/Spalten, Runtime-CAS und Serialisierung, Audit-Immutability, Idempotenz, terminale Guards, Result-Selection, Backfill aus 2407, Constraint-Validierung, Steam-V1-Generation/Leases, Privacy-Redaction und Registry-Abdeckung. rust/scripts/central_fresh_schema.sh bindet den Foundation-Testlauf in den frischen Schema-Drift-Check ein.
Rollback Die Migrationen enthalten keine Down-Migrationen. Vor Anwendung ist Rollback trivial: Migrationen nicht ausführen. Während einer fehlgeschlagenen Migration wird die jeweilige Migration transaktional abgebrochen. Nach erfolgreicher Anwendung ist der sichere Rollback-Pfad ein Datenbank-Snapshot oder ein explizit reviewed DB-Rollback, weil mehrere Tabellen append-only oder delete-geschützt sind und Backfill-Daten bewusst nicht hart gelöscht werden.

Explizite Nicht-Ziele

  • Kein Writer-Cutover von dl-bots auf turniere. Der Runtime-Seed bleibt legacy/dl-bots.
  • Kein Identity-Cutover der bestehenden Scrim-Tabellen und keine neuen Identity-Defaults auf Legacy-ID-Spalten.
  • Kein Steam-V1-Consumer, keine Aktivierung von Capability-Flags und kein automatischer Start von Steam-V1-Workflows.
  • Keine neue HTTP-, Discord- oder Bot-API. Die Migrationen definieren Datenbankverträge.
  • Kein Versand von Announcements, Status-Publications oder Replacement-Requests; es werden nur Persistenz- und Approval-Objekte angelegt.
  • Keine harte Löschung von Result-Refs als Fachoperation. Result-Refs werden soft-voided, superseded oder canonical ausgewählt.
  • Kein neuer nichtkonkurrenter Index auf der Live-Tabelle scrim.match_result_refs; diese Review ist ausdrücklich nach Cutover vertagt.
  • Kein Ersetzen von steam.steam_tasks. Steam-V1 kann optional auf Legacy-Tasks referenzieren, aber der Legacy-Vertrag bleibt bestehen.

Quellen: Datenbank-Migrationen 2026072408 bis 2026072416, Foundation-Tests und Privacy-Vertrag. Keine Secrets, keine externen Ressourcen.
